# 共享数据库和服务适配方案

目标：每个节点使用一个记录数据库、一个 TeslaMate 记录进程、一个 TeslaMateAPI 进程；数据库连接池、MQTT 连接和 PostgreSQL LISTEN 按节点共享，不按租户复制。租户状态、OAuth、车辆、通知接收人和业务数据仍独立。

## 存储决策

采用单数据库、每租户独立 schema。保留各租户原表结构与本地 ID，避免合库时修改 positions / drives / charges 的全部历史外键和统计口径。公共扩展保留在公共 schema；tokens/OAuth 等私有表存于租户对应的私有 schema。数据库名与连接凭据统一，租户目录增加经过严格校验的 schema 名；schema 与 tenant_id 的映射只来自受信控制平面。

连接池上限由节点配置固定。连接不能把上个租户的 search_path、role 或事务状态带到下个租户。所有 SQL（包括统计原生 SQL、事务、后台任务及通知查询）必须使用显式租户上下文；共享模式缺失上下文时拒绝业务查询。原有每库模式保留用于迁移和回滚，不能混淆为 Owner API 兼容。

## API 服务

将包级可变业务状态改为租户运行时对象，复用原路由、计算与响应协议。一个 HTTP 监听器通过已验证 AK/SK 凭据选择运行时，不相信裸 tenant_id 或客户端自报的 schema。每个租户有独立状态缓存、时区、通知配置与任务归属；数据库连接由统一物理池提供。

必须覆盖同一时刻两个租户均有 car_id=1、drive_id=1 的情况；缓存、去重、回放保护、Live Activity、APNS 接收人和充电通知均不能串租户。

## MQTT 与通知

记录器用共享 broker 连接发布，各租户保持唯一 namespace。API 一个连接订阅允许的租户 namespace，将消息分派给对应运行时，不使用跨租户 car_id 索引。租户撤销/停用应立即阻断 HTTP 与消息路由。

PostgreSQL 通知采用一个 LISTEN 连接；通知载荷必须带可信数据库 schema，路由到对应租户。所有触发器与应用侧通知发送点都须适配，不能只修改 MQTT。

## 管理端与 App

控制平面新开通时分配共享数据库内的 schema、车辆 namespace、API 凭据和共享 API 地址，不再创建每租户 API 容器或数据库连接用户。续费、停用、恢复、删除及重置走同一模式；共享 schema 的删除不能误删整个数据库。已有部署需要显式迁移，不自动修改线上数据。

客户端沿用 tenant.api 连接契约；Fleet 授权由官方中国 OAuth 取代原 Owner 授权。新授权能力由控制平面声明，回调与当前用户/安装会话绑定。

## 验证要求

- 原 Fleet 回归与真实接收器 → Kafka → 入库联调继续保留。
- 两租户同 ID 并发读写、事务回滚、连接归还、后台任务、统计及缓存隔离。
- MQTT 同 ID 不串车、停止租户不再发通知、数据库 LISTEN 路由、APNS 目标隔离。
- 控制面新开通/重新同步幂等、停用/恢复、共享模式删除保护、迁移及回滚演练。
- 单节点连接数随并发上限变化，不能随租户数线性增加；记录实测连接数与测试规模。
- App API 契约、官方 OAuth 用户路径、Swift 完整构建；无法执行的实车或 Simulator 验证明确保留待验收。

所有改动各仓库独立分支，不合并或部署线上。
